# 验证消息通过持久投递 outbox 发送

Status: accepted

注册验证、密码重置和后续联系方式操作通过 PostgreSQL 持久 outbox 接受投递任务，HTTP 请求不在响应路径中连接 SMTP。对格式有效的请求，公开响应不因联系方式是否存在、占用、可恢复或单封投递结果而改变；独立 worker 以有界重试投递，同一逻辑任务重复执行只能重发同一个 challenge，不能创建多个并发有效验证码。全局服务熔断只有在与具体账号无关并对所有请求一致时才能返回服务不可用。

验证码由密码学安全随机源生成；challenge 的长期字段只保存带独立 pepper 的摘要，outbox 只在投递终结前保存由另一把可轮换密钥加密的投递 payload。worker 重试必须重发同一逻辑 challenge 的同一个验证码；provider 接受后才激活 challenge 并擦除 payload，在此之前旧 active challenge 继续有效。provider 接受与本地确认之间的崩溃可以导致同一个码被重复投递，但不能产生多个有效码。

验证码 TTL 从成功激活开始，重发冷却从 HTTP 请求被接受开始。request 使用 Idempotency-Key 收敛网络重试；客户端不获得 challenge identity 或投递状态查询能力，也不自动重发。投递、限流或密钥依赖整体不可用时，验证功能对所有请求一致地失败关闭，账号名和密码登录保持独立可用。

选择 outbox 是为了让非枚举响应、进程重启后的可靠投递和 SMTP 超时隔离使用同一边界。考虑过在 HTTP 请求中同步发信并增加固定延时，以及直接返回邮件提供商结果；前者仍泄漏显著的时序差异并把网络延迟带入认证请求，后者直接泄漏账号资格，因此不采用。
