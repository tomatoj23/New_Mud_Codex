## 二、项目定位

### 2.1 项目目标

构建一款中文武侠题材的多人在线文字 MUD。

项目采用自研引擎 + 可替换 MUDLib 的架构。

项目支持 Web 与微信小程序接入。

项目以纯文字体验为主，预留图标、图片、音效扩展接口。

### 2.2 总体原则

- 不使用 Evennia 作为运行时框架。
- 借鉴 Evennia 的设计思想，不复用其 Twisted 运行时、进程模型、管理后台扩展。
- 后端采用模块化单体架构，不做微服务拆分。
- 一个服务器实例只加载一个 MUDLib。
- V1 只做单实例纵向扩展，不做多实例水平扩展。
- 内容与规则可扩展，代码热更新不作为 V1 目标。

### 2.3 借鉴 Evennia 的范围

- 借鉴对象抽象方式：Typeclass 思想。
- 借鉴命令系统与权限校验思路。
- 借鉴周期任务与世界事件的 Script 思想。
- 借鉴对象生命周期 Hook 设计。

### 2.4 明确不借鉴的范围

- 不使用 Evennia 的 Twisted + Autobahn 网络栈。
- 不使用 Evennia 自带 Admin 扩展。
- 不使用 Evennia 的进程守护与 Portal/Server 进程模型。
- 不要求与 Evennia 工程结构兼容。

## 三、确认后的技术路线

### 3.1 后端主栈

- 语言：Python 3.12+
- Web 框架：Django
- REST API：Django REST Framework
- 实时通信：Django Channels
- ASGI 服务：Daphne
- 数据库：PostgreSQL
- Redis：Channels channel layer、在线状态、短期缓存、分布式锁、限流辅助
- 后台任务：Celery + Redis

### 3.2 前端主栈

- 框架：uni-app（Vue 3）
- 状态管理：Pinia
- 首发平台：H5、微信小程序
- PC 端通过 H5 提供增强输入体验

### 3.3 管理后台

- 使用 Django Admin 作为后台基础。
- 根据内容管理需求扩展自定义 ModelAdmin、管理页面与批处理工具。
- 不依赖 Evennia Admin 代码。

### 3.4 数据库策略

- 开发、测试、生产统一使用 PostgreSQL。
- SQLite 仅允许用于个人实验，不作为主线环境。
- 所有正式模型、迁移、索引策略均以 PostgreSQL 为准。

### 3.5 任务与调度边界

- 高频游戏节拍由引擎内 Scheduler/Tick Service 负责。
- 低频异步任务由 Celery 负责。
- Celery 用于短信、微信回调、导出、备份触发、低频定时任务。
- 战斗节拍、NPC 作息、世界时钟不交给 Celery。

### 3.6 架构形态

- 架构采用“模块化单体 + 单数据库 + Redis”。
- 不做服务拆分。
- 不做事件总线中台。
- 不做跨实例状态同步。

## 四、运行时架构

### 4.1 HTTP/API 层

职责如下：

- 注册、登录、刷新 Token
- 角色创建与角色列表
- 背包、武学、任务等非高频查询
- 后台管理接口
- 微信登录与支付预留接口

### 4.2 WebSocket 实时层

职责如下：

- 游戏主交互流
- 房间广播
- 战斗事件推送
- 聊天频道
- 组队状态同步
- 在线状态变化

客户端与服务端通过统一事件信封通信。

事件信封包含 `type`、`request_id`、`payload`、`version`。

### 4.3 游戏应用层

职责如下：

- 命令解析与路由
- 权限与前置条件校验
- 房间移动与场景交互
- 战斗结算
- 任务推进
- 交易校验
- 帮派与声望变更

### 4.4 游戏调度层

职责如下：

- 世界时间推进
- NPC 作息切换
- 定时刷新
- 战斗回合推进
- BUFF/DEBUFF 生命周期
- 随机事件触发

调度层是引擎核心，不依赖第三方任务队列的执行语义。

### 4.5 异步作业层

职责如下：

- 发送短信验证码
- 处理微信异步回调
- 数据导入导出
- 备份触发
- 审计日志汇总

### 4.6 后台与内容制作层

职责如下：

- 世界内容编辑
- NPC/物品/武学配置
- 任务配置
- 账号运营与封禁
- 公告管理
- 数据巡检与修复工具

## 五、引擎设计

### 5.1 核心对象模型

引擎采用“基础类型 + 组件/Handler 组合”的对象模型。

保留 Typeclass 思想，但避免深层继承失控。

基础实体包括：

- Account
- Character
- Room
- Exit
- NPC
- Item
- Skill
- Buff
- Quest
- Faction
- CombatInstance

### 5.2 原型与实例

- 原型用于定义静态模板。
- 实例用于承载运行时状态。
- 可转换的 MUDLib 数据优先落为原型数据。
- 玩家角色、掉落物、战斗状态属于实例数据。

### 5.3 组件与 Handler

建议优先采用组合，而不是持续增加继承层级。

可复用组件包括：

- CombatComponent
- InventoryComponent
- EquipmentComponent
- DialogueComponent
- AIComponent
- TradeComponent
- QuestGiverComponent

### 5.4 生命周期 Hook

引擎统一提供以下 Hook：

- `at_spawn`
- `at_enter`
- `at_leave`
- `at_receive_command`
- `at_tick`
- `at_combat_start`
- `at_combat_end`
- `at_destroy`

MUDLib 只能使用公开 Hook 与服务接口扩展行为。

### 5.5 命令系统

客户端按钮、快捷键、文本输入最终统一进入同一命令总线。

命令处理顺序如下：

1. 输入标准化
2. 命令识别
3. 权限与状态校验
4. 业务执行
5. 事件输出
6. 日志与审计记录

命令系统必须同时支持：

- 文字命令输入
- UI 按钮触发
- 快捷键映射
- 管理员命令

### 5.6 Script 与效果系统

V1 不允许从转换后的 LPC 直接执行任意 Python 代码。

效果系统分为三类：

- 配置型效果：纯数据驱动
- 规则型效果：调用引擎内公开规则函数
- 人工适配效果：由开发者实现并登记

长周期逻辑通过 Scheduler 注册。

短周期战斗效果通过 Buff/Effect 生命周期管理。

### 5.7 服务边界

引擎公共服务包括：

- ChatService
- CombatService
- MovementService
- QuestService
- ReputationService
- TradeService
- WeatherTimeService
- PathfindingService

MUDLib 不应直接依赖底层私有 ORM 细节。

## 六、MUDLib 架构

### 6.1 目标

MUDLib 负责定义世界内容、数值规则、门派体系、任务与事件。

引擎负责提供通信、存储、调度、命令路由与公共服务。

### 6.2 基本约束

- 每个 MUDLib 为独立 Python 包。
- 启动时通过配置指定加载目标 MUDLib。
- 运行中不切换 MUDLib。
- 一个实例只加载一个 MUDLib。

### 6.3 推荐目录契约

每个 MUDLib 至少包含以下内容：

- `manifest.py`：名称、版本、依赖、入口声明
- `content/`：房间、NPC、物品、武学、任务等静态数据
- `rules/`：战斗公式、成长规则、掉落规则
- `hooks/`：公开 Hook 适配代码
- `converter_profile/`：LPC 转换配置
- `tests/`：MUDLib 自测

### 6.4 加载边界

启动流程如下：

1. 读取引擎配置
2. 加载目标 MUDLib manifest
3. 注册内容定义
4. 注册规则与 Hook
5. 执行启动期校验
6. 启动世界

### 6.5 热更新边界

V1 支持有限内容热更新。

允许热更新的范围：

- 文本描述
- 配置表
- 部分数值参数
- 非结构性任务文本

不允许热更新的范围：

- Python 规则代码
- 模型结构
- 核心引擎逻辑

代码更新统一通过重启发布。

## 七、LPC MUDLib 转换器

### 7.1 转换目标

首个目标为 XKX100。

转换策略为一次性导入，不保持与源 MUDLib 的持续同步。

### 7.2 转换总原则

- 先转结构与静态数据。
- 再转规则与脚本骨架。
- 复杂逻辑允许生成“人工适配清单”。
- 不追求对 LPC 运行时的完整模拟。

### 7.3 转换管线

转换流程如下：

1. 源码扫描
2. 继承关系分析
3. 宏与公共定义抽取
4. Daemon 引用识别
5. 房间/NPC/物品/技能转中间表示
6. 中间表示生成目标数据
7. 生成人工适配报告
8. 导入并校验

### 7.4 自动转换范围

可自动转换的内容包括：

- 房间与出口拓扑
- 静态 NPC/物品属性
- 区域结构
- 技能基础定义
- 商店货品清单
- 纯配置型对话与文本

### 7.5 半自动转换范围

需要人工审核的内容包括：

- 战斗公式
- 特殊技能效果
- Daemon 行为
- 复杂任务条件
- 跨文件动态调用
- 数据库存取代码

### 7.6 不纳入 V1 的能力

- 不做 LPC 代码即时解释执行。
- 不做源 MUDLib 双向同步。
- 不保证 100% 保留原行为细节。

### 7.7 转换配置项

转换器需支持以下配置：

- mudlib 根目录偏移
- 基类路径映射
- 技能目录映射
- Daemon 路径映射
- API 风格识别
- 特殊文件排除规则
- 保存文件导入策略

### 7.8 输出产物

每次转换至少输出：

- 结构化内容数据
- 规则骨架代码
- 转换日志
- 未适配项清单
- 导入校验报告

## 八、账号与认证

### 8.1 账号体系

- 支持手机号注册
- 支持微信小程序授权登录
- 两种方式可绑定同一账号
- 单账号最多创建 10 个角色

### 8.2 认证策略

玩家侧认证采用 JWT + Refresh Token。

管理后台采用 Django Session/Cookie。

两套认证边界必须分离。

### 8.3 安全要求

- 密码哈希采用 Django 标准密码哈希体系
- 手机号等敏感字段加密存储
- 验证码与登录接口限流
- 支持异地登录检测
- 关键账号操作进入审计日志

## 九、前端与多端接入

### 9.1 支持平台

- PC 浏览器
- 移动端浏览器
- 微信小程序

### 9.2 一致性原则

三端保持核心流程一致。

三端不强求完全一致的交互细节。

PC 端允许增强键盘输入与窗口布局。

小程序端允许为平台限制做轻量调整。

### 9.3 主交互模型

客户端主界面包含：

- 场景描述区
- 事件流区
- 命令输入区
- 快捷操作区
- 状态区
- 聊天区

### 9.4 PC 端增强能力

- 命令历史
- 自动补全
- 快捷键
- 面板布局优化
- 更强的文本可读性配置

### 9.5 小程序端约束

- 避免依赖复杂悬浮交互
- 避免依赖连续键盘操作
- 网络波动下优先保证文本事件流可恢复

### 9.6 表现层扩展

V1 以纯文字为主。

保留以下扩展接口：

- 图标
- 图片插槽
- 音效开关
- 主题配置

## 十、核心玩法范围

### 10.1 MVP 目标

MVP 的目标不是一次做完整武侠世界。

MVP 的目标是打通“可注册、可进世界、可移动、可战斗、可聊天、可管理内容”的闭环。

### 10.2 MVP 必做能力

- 注册、登录、角色创建
- 房间/出口/场景浏览
- 基础移动与查看
- 公共聊天、私聊、帮派频道
- 基础 PvE 战斗
- 简化 PvP 竞技场
- 背包、装备、物品使用
- 基础任务系统
- 基础门派/帮派加入
- 玩家间交易
- Web 管理后台
- 首个 MUDLib 的可导入内容样板

### 10.3 MVP 战斗策略

V1 只实现一套统一战斗结算框架。

MVP 默认采用“限时回合制”。

即时制与多战斗模式切换不纳入首发目标。

### 10.4 MVP 地图策略

V1 以房间图为核心。

数据层允许房间带 `z` 坐标。

MVP 不实现复杂的区域流式加载系统。

自动寻路仅支持房间图级别的 A*。

### 10.5 MVP 世界动态

MVP 支持以下动态能力：

- 昼夜切换
- 基础 NPC 作息
- 简化随机遭遇
- 基础声望变化

以下能力延后：

- 季节系统深度联动
- 因果系统复杂分支
- 大规模世界状态演化

### 10.6 首发后迭代方向

- 更复杂的武学联动
- 自创武学
- 多周目与传承
- 高级门派体系
- 复杂秘境与大型事件
- 音效与图形化增强
