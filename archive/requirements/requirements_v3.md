## 二、项目定位与边界

### 2.1 项目目标

构建一款中文武侠题材的多人在线文字 MUD。

项目采用自研引擎 + 可替换 MUDLib 的架构。

项目支持 Web 与微信小程序接入。

项目以纯文字体验为主，预留图标、图片、音效扩展接口。

### 2.2 总体原则

- 不使用 Evennia 作为运行时框架。
- 借鉴 Evennia 的设计思想，但不复用其运行时代码。
- 后端采用模块化单体架构。
- 只做单实例。
- 不做多实例水平扩展。
- 不做跨实例状态同步。
- 一个服务器实例只加载一个 MUDLib。
- 运行中不切换 MUDLib。
- 内容与规则可扩展。
- 代码热更新不作为目标。
- 只允许有限内容热更新。
- 首发闭环优先于长期能力完整度。

### 2.3 借鉴 Evennia 的范围

- 借鉴 Typeclass 思想。
- 借鉴命令系统与权限校验思路。
- 借鉴对象生命周期 Hook 设计。
- 借鉴 Script、Scheduler、世界事件的抽象方式。
- 借鉴 Blueprint / Prototype 的分层思路。
- 借鉴房间、出口、对象、角色的统一实体建模方式。

### 2.4 明确不借鉴的范围

- 不使用 Evennia 的 Twisted + Autobahn 网络栈。
- 不使用 Evennia 的 Portal / Server 双进程模型。
- 不使用 Evennia 自带 Admin 扩展。
- 不复用 Evennia 的 Attribute 魔法层作为项目主状态模型。
- 不要求兼容 Evennia 的目录结构、加载流程与对象实现。

### 2.5 首发边界概述

首发闭环不是完整武侠大世界。

首发闭环只要求打通以下最小链路：

- 可登录
- 可进世界
- 可查看
- 可移动
- 可聊天
- 可即时战斗
- 可使用基础物品
- 可通过后台编辑内容

以下能力移出首发闭环：

- 短信验证码
- 微信授权登录
- 帮派系统
- XKX100 首轮转换验收

## 三、技术路线与调整结论

### 3.1 调整结论

基于新增约束，技术栈需要做有限调整。

调整原则不是推翻 V2，而是降低首发复杂度，收紧单实例边界。

本轮调整结论如下：

- `Django + DRF + Channels + PostgreSQL` 仍然保留。
- `uni-app + Vue 3 + Pinia` 仍然保留。
- `Redis` 不再承担分布式锁职责。
- `Celery` 不再作为首发闭环的必选基础设施。
- 首发核心运行时以单实例、单写者、进程内调度为准。

### 3.2 后端核心必选栈

- 语言：Python 3.12+
- Web 框架：Django
- REST API：Django REST Framework
- 实时通信：Django Channels
- ASGI 服务：Daphne
- 数据库：PostgreSQL

### 3.3 前端核心栈

- 框架：uni-app（Vue 3）
- 状态管理：Pinia
- 首发平台：H5、微信小程序
- PC 端通过 H5 提供增强输入体验

### 3.4 推荐但非首发必选的基础设施

以下技术保留为推荐能力，但不强制成为首发闭环前置：

- Redis
- Celery
- Celery Beat
- 外部对象存储
- 专用消息告警平台

### 3.5 Redis 的定位

Redis 在 V3 中不是首发核心必选项。

它的定位调整为按需引入的基础设施。

允许的用途包括：

- Channels 的 Redis channel layer
- 在线状态辅助缓存
- 短期缓存
- 限流辅助

不允许把 Redis 写成“多实例协调前提”，因为本项目只做单实例。

### 3.6 Celery 的定位

高频游戏节拍由引擎内 Scheduler / Tick Service 负责。

战斗节拍、技能冷却、BUFF 生命周期不交给 Celery。

首发闭环不要求 Celery。

后续若接入以下能力，再按需引入 Celery：

- 短信验证码发送
- 微信异步回调处理
- 数据导出
- 定时备份触发
- 低频审计汇总任务

### 3.7 单实例并发控制策略

单实例前提下，优先采用以下并发控制方式：

- PostgreSQL 事务
- 行级锁
- 乐观版本号
- 进程内锁

明确不引入以下语义：

- 分布式锁
- 跨实例一致性协议
- 跨实例 Presence 同步
- 事件总线中台

### 3.8 数据库策略

- 开发、测试、生产统一使用 PostgreSQL。
- SQLite 仅允许用于个人实验，不作为主线环境。
- 所有正式模型、迁移、索引策略均以 PostgreSQL 为准。
- 所有首发性能判断均以 PostgreSQL 行为为准。

## 四、运行时架构

### 4.1 HTTP / API 层

职责如下：

- 登录、登出、刷新 Token
- 角色创建与角色列表
- 背包、武学、任务等非高频查询
- 后台管理接口
- 后续预留手机号、微信、支付接入点

### 4.2 WebSocket 实时层

职责如下：

- 游戏主交互流
- 房间广播
- 战斗事件推送
- 聊天消息推送
- 在线状态变化
- 即时技能释放结果回传

客户端与服务端通过统一事件信封通信。

事件信封基础字段如下：

- `type`
- `request_id`
- `payload`
- `version`

服务端推送事件建议额外包含：

- `seq`
- `ts`

### 4.3 WebSocket 可靠性原则

V1 不做复杂实时帧同步。

但必须定义最基本的恢复策略：

- 客户端断线重连后可恢复当前角色状态摘要。
- 事件流允许按 `seq` 做增量补齐或安全重建。
- 关键动作必须有显式失败反馈。
- 客户端不得根据本地预测直接修改权威状态。

### 4.4 游戏应用层

职责如下：

- 命令解析与路由
- 权限与前置条件校验
- 房间移动与场景交互
- 战斗结算
- 任务推进
- 交易校验
- 声望与组织关系变更
- 内容与交互事件输出

### 4.5 游戏调度层

职责如下：

- 世界时间推进
- NPC 作息切换
- 定时刷新
- 技能冷却到期
- BUFF / DEBUFF 生命周期
- 随机事件触发
- 非战斗中的周期世界逻辑

调度层是引擎核心，不依赖第三方任务队列的执行语义。

### 4.6 权威状态与持久化边界

以下状态以 PostgreSQL 为持久化真源：

- User
- GameAccount
- Character
- 物品实例
- 房间与出口拓扑
- 任务进度
- 声望与组织关系
- 内容定义与原型数据

以下状态以单实例运行时内存为主：

- 在线 Presence
- 房间订阅关系
- 活跃 CombatInstance
- 技能冷却计时
- 短周期调度队列
- 短期 UI 推送上下文

关键结算结果必须回写 PostgreSQL。

### 4.7 故障恢复原则

进程重启后，短期运行时状态允许丢失，但必须有安全回退策略。

例如：

- 战斗中断后角色回到非战斗状态。
- 临时冷却丢失时重新按持久化时间戳恢复或安全重置。
- 在线 Presence 全量重建。
- 活跃交互上下文在无法恢复时安全失效，而不是半残留。

## 五、核心领域与引擎设计

### 5.1 核心对象模型

引擎采用“基础类型 + 组件 / Handler 组合”的对象模型。

保留 Typeclass 思想，但避免深层继承失控。

基础实体至少覆盖以下范围：

- User
- AuthIdentity
- GameAccount
- Character
- Area / Region
- Room
- Exit
- NPC
- Item
- Skill
- SkillMove
- Neigong
- Buff
- Quest
- Dialogue
- Shop
- Reputation / Faction
- LootTable
- Trigger
- CombatInstance

### 5.2 核心实体的定位

| 实体 | 主要职责 | 典型持久化内容 | 首发要求 |
|:---|:---|:---|:---|
| User | 认证与后台授权主体 | 登录凭据、后台角色 | 必做 |
| GameAccount | 玩家游戏域账号 | 角色归属、玩家侧关系 | 必做 |
| Character | 玩家可控角色 | 属性、背包、任务、声望 | 必做 |
| Room | 场景与容器边界 | 描述、区域、坐标、细节 | 必做 |
| Exit | 房间连接关系 | 起点、终点、条件 | 必做 |
| NPC | 非玩家角色 | 对话、AI、掉落、商店等 | 必做 |
| Item | 可拾取或可交互对象 | 分类、效果、绑定、耐久 | 必做 |
| Skill / SkillMove | 武学与招式定义 | 消耗、冷却、效果、条件 | 必做 |
| Buff | 短中期状态效果 | 来源、持续时间、叠层 | 必做 |
| Quest | 任务定义与进度 | 阶段、条件、奖励 | 基础版必做 |
| Dialogue | 对话树与文本 | 节点、条件、选项 | 基础版推荐 |
| Shop | 商店定义 | 货品、价格、限制 | 推荐 |
| Reputation / Faction | 声望与组织关系 | 正邪、门派、组织归属 | 基础版推荐 |
| CombatInstance | 活跃战斗上下文 | 参战方、目标、战斗状态 | 必做 |

### 5.3 内容框架覆盖原则

本项目的内容框架应尽可能覆盖更广的 MUDLib 内容形态。

目标不是只适配已知样本。

目标是形成一套可承接更多 MUDLib 的通用内容骨架。

因此引擎内容层应优先支持以下类别：

- 世界拓扑
- 静态实体定义
- 技能与效果定义
- perform / exert / special 等武学衍生能力
- 对话与商店
- 任务与触发器
- 阵营、门派、帮派与声望
- 条件、毒素、疾病、封脉等持续状态
- 掉落与刷新
- 交互条件与可见性规则
- 状态效果与持续性逻辑
- 师承、职业 / class、商贩、守卫等 NPC 角色类型
- 私有空间、迷宫模板、建造模板等特殊场景形态
- 命令、别名、权限层级等玩法入口元数据

对于某些旧 MUDLib 没做到的内容，框架仍可预留统一位置。

### 5.4 原型与实例

- 原型用于定义静态模板。
- 实例用于承载运行时状态。
- 可转换的 MUDLib 数据优先落为原型数据。
- 玩家角色、掉落物、战斗状态属于实例数据。
- 原型必须支持版本号与来源标记。
- 原型必须支持审核、发布与回滚的最小流程。

### 5.5 组件与 Handler

建议优先采用组合，而不是持续增加继承层级。

可复用组件包括：

- CombatComponent
- InventoryComponent
- EquipmentComponent
- DialogueComponent
- AIComponent
- TradeComponent
- QuestGiverComponent
- CooldownComponent
- ReputationComponent
- VisibilityComponent

### 5.6 生命周期 Hook

引擎统一提供以下 Hook：

- `at_spawn`
- `at_enter`
- `at_leave`
- `at_receive_command`
- `at_tick`
- `at_skill_cast`
- `at_damage`
- `at_combat_start`
- `at_combat_end`
- `at_destroy`

MUDLib 只能使用公开 Hook 与服务接口扩展行为。

### 5.7 命令系统

客户端按钮、快捷键、文本输入最终统一进入同一命令总线。

命令处理顺序如下：

1. 输入标准化
2. 命令识别
3. 权限与状态校验
4. 业务执行
5. 事件输出
6. 日志与审计记录

命令系统必须同时支持：

- 文字命令输入
- UI 按钮触发
- 快捷键映射
- 管理员命令

### 5.8 Script 与效果系统

V1 不允许从转换后的 LPC 直接执行任意 Python 代码。

效果系统分为三类：

- 配置型效果：纯数据驱动
- 规则型效果：调用引擎内公开规则函数
- 人工适配效果：由开发者实现并登记

长周期逻辑通过 Scheduler 注册。

短周期战斗效果通过 Buff / Effect 生命周期管理。

### 5.9 公共服务边界

引擎公共服务包括：

- ChatService
- CombatService
- MovementService
- QuestService
- ReputationService
- TradeService
- WeatherTimeService
- PathfindingService
- ContentSyncService

MUDLib 不应直接依赖底层私有 ORM 细节。

## 六、MUDLib 架构

### 6.1 目标

MUDLib 负责定义世界内容、数值规则、门派体系、任务与事件。

引擎负责提供通信、存储、调度、命令路由与公共服务。

### 6.2 必须区分的两类 MUDLib

本项目中必须明确区分以下两类 MUDLib：

- 原生 MUDLib：面向本项目自研引擎的 Python 内容包。
- 源 LPC MUDLib：用于分析、转换、参考的历史 LPC 代码库。

两者不是同一概念。

原生 MUDLib 需要遵守本项目的加载契约。

源 LPC MUDLib 不要求遵守本项目目录结构。

转换器的职责是把源 LPC MUDLib 归一化为本项目可消费的数据与适配骨架。

### 6.3 基本约束

- 每个原生 MUDLib 为独立 Python 包。
- 启动时通过配置指定加载目标原生 MUDLib。
- 运行中不切换 MUDLib。
- 一个实例只加载一个 MUDLib。

### 6.4 本地样本揭示的现实约束

基于本地 `D:\My_Projects\Mudlibs` 中的样本，可确认以下事实：

- 不同 MUDLib 的根目录风格差异很大。
- 有的以 `/adm /cmds /d /daemon /obj /std` 为主。
- 有的把这些目录全部包在 `world/` 下。
- 有的把技能拆到 `kungfu/skill`，把类 NPC 拆到 `kungfu/class`。
- 有的额外存在 `inherit/`、`clone/`、`feature/`、`b/`、`u/`、`world/builds/` 等目录。

因此，不能把某一种目录布局写成通用前提。

MUDLib 兼容层必须以“语义角色”识别内容，而不是以固定目录名识别内容。

### 6.5 源 LPC MUDLib 中常见的语义区域

从样本看，源 LPC MUDLib 通常会出现以下语义区域：

| 语义区域 | 常见目录示例 | 作用 | 转换处理方式 |
|:---|:---|:---|:---|
| 系统与安全 | `adm/`、`world/adm/` | 核心 daemon、权限、安全、配置 | 主要做扫描与引用分析 |
| 玩家命令 | `cmds/usr`、`cmds/std` | 玩家玩法入口 | 记录命令语义，不直接逐条移植 |
| 管理命令 | `cmds/wiz`、`cmds/imm`、`cmds/arch`、`cmds/adm` | 巫师与维护命令 | 作为后台需求参考，不直接兼容 |
| 世界区域 | `d/`、`world/d/`、`world/area/` | 房间、出口、区域、NPC、场景物件 | 核心转换目标 |
| 技能体系 | `daemon/skill`、`d/skill`、`kungfu/skill` | 技能、招式、perform、exert | 核心转换目标 |
| 门派 / class | `daemon/class`、`kungfu/class` | 师承、门派、类 NPC、技能派生 | 核心转换目标 |
| 条件系统 | `daemon/condition` | 毒、伤、封脉、异常状态 | 核心转换目标 |
| 物品体系 | `obj/`、`clone/`、`d/obj/` | 武器、防具、药物、书籍、货币、任务物品 | 核心转换目标 |
| 基类与 mixin | `std/`、`inherit/`、`feature/` | 房间/NPC/物品基类、行为复用层 | 必须分析继承与能力来源 |
| 巫师工作区 | `u/` | 巫师实验内容与临时世界 | 默认不纳入自动正式导入 |
| 建造模板 / 私有区 | `b/`、`world/builds/` | 玩家建造、迷宫模板、私有空间、样板房 | 归为高级内容，首轮半自动处理 |
| 数据与存档 | `data/`、`backup/`、`topten/` | 存档与离线数据 | 按配置决定是否导入 |
| 文档与网页 | `doc/`、`help/`、`www/` | 文档、帮助、网页端资源 | 参考导入，不作为核心玩法对象 |

### 6.6 兼容抽象原则

MUDLib 兼容抽象必须遵守以下原则：

- 先识别语义角色，再决定目标模型。
- 目录名称只作为线索，不作为唯一依据。
- 继承链、宏定义、路径宏和 include 文件必须进入分析范围。
- `__DIR__`、`SKILL_D`、`CLASS_D`、`ITEM_D`、`NPC_D` 等路径展开必须被识别。
- `std/`、`inherit/`、`feature/` 中的基础能力必须被视为定义来源。
- `replace_program(ROOM)`、坐标字段、地图标签、动态刷怪等都是合法变体。
- 无法归一化的行为必须明确进入人工适配清单。

### 6.7 源内容与目标内容的边界

引擎最终消费的是“归一化后的目标内容”，而不是源 LPC 目录本身。

目标内容至少要归一化为以下层次：

- 世界层：区域、房间、出口、坐标、地图标签、刷新点。
- 角色层：玩家角色、普通 NPC、门派师父、商贩、守卫、特殊事件 NPC。
- 物品层：武器、防具、药物、书籍、货币、材料、任务物品、容器。
- 武学层：技能、招式、perform、exert、special、练习 / 学习条件。
- 状态层：condition、buff、debuff、毒、伤、封脉、忙乱。
- 任务层：任务节点、条件、奖励、流程状态。
- 组织层：门派、师承、阵营、帮派、组织身份。
- 规则层：公式、冷却、掉落、刷新、AI、触发器。
- 系统层：daemon 引用、命令元数据、后台辅助信息。

### 6.8 原生 MUDLib 的目标契约

原生 MUDLib 应作为本项目引擎的内容包存在。

它应满足以下目标契约：

- 有一个 manifest 作为入口。
- 能显式声明版本、依赖、兼容的引擎版本。
- 能注册内容定义、规则函数、Hook 适配与后台扩展项。
- 能声明转换器 profile 和导入规则。
- 能提供最小自测。

### 6.9 推荐目录契约

以下目录是原生 MUDLib 的推荐契约，而不是对源 LPC MUDLib 的要求：

每个 MUDLib 至少包含以下内容：

- `manifest.py`：名称、版本、依赖、入口声明
- `content/`：房间、NPC、物品、武学、任务等静态数据
- `content_ext/`：组织、商店、对话、掉落、刷新、地图标签等扩展定义
- `rules/`：战斗公式、成长规则、掉落规则
- `hooks/`：公开 Hook 适配代码
- `adapters/`：人工适配逻辑与兼容桥接
- `converter_profile/`：LPC 转换配置
- `reports/`：转换报告与人工适配报告归档
- `tests/`：MUDLib 自测

如果内部不完全采用该目录，只要 manifest 能完成显式注册，也允许接受。

### 6.10 加载边界

启动流程如下：

1. 读取引擎配置
2. 加载目标 MUDLib manifest
3. 注册内容定义
4. 注册规则与 Hook
5. 执行启动期校验
6. 启动世界

### 6.11 MUDLib 公开接口原则

MUDLib 只能通过以下方式扩展引擎：

- 注册内容定义
- 注册规则函数
- 注册 Hook 适配
- 调用公开服务接口
- 注册命令元数据与 UI 动作映射
- 注册后台内容编辑 schema
- 注册转换器 profile 与人工适配器

MUDLib 不应直接：

- 操作私有 ORM 细节
- 越过服务层写跨域状态
- 执行未经登记的任意 Python 代码片段
- 假设运行时是 Evennia 风格对象系统
- 假设源 LPC MUDLib 的目录结构会在目标引擎中原样存在
- 假设 `cmds/`、`daemon/`、`std/` 会被目标项目一比一保留

### 6.12 MUDLib 能力分层

为了兼容更多 mudlib，同时避免所有东西都变成“脚本魔法”，MUDLib 能力分为四层：

| 层级 | 内容 | 说明 |
|:---|:---|:---|
| L1 静态内容层 | 房间、出口、NPC、物品、文本、商店、基础技能 | 最稳定，最适合自动转换与后台编辑 |
| L2 规则配置层 | 冷却、消耗、掉落、刷新、条件、权重、公式参数 | 可配置为主，必要时辅以规则函数 |
| L3 公开规则层 | 技能判定、AI 决策、触发器、战斗结算挂点 | 通过白名单接口扩展 |
| L4 人工适配层 | 无法自动归一化的特殊玩法逻辑 | 必须登记、审计、测试 |

V1 应优先把更多内容收敛到 L1 与 L2。

### 6.13 有限热更新边界

V1 支持有限内容热更新。

允许热更新的范围：

- 文本描述
- 配置表
- 部分数值参数
- 部分对话文本
- 非结构性任务文本

不允许热更新的范围：

- Python 规则代码
- 模型结构
- 房间拓扑结构
- 核心引擎逻辑
- CombatService 的算法实现

代码更新统一通过重启发布。

### 6.14 实例同步规则

有限热更新必须遵守以下实例同步规则：

1. 所有内容定义必须带版本号。
2. 新生成实例总是使用最新版本定义。
3. 已存在实例不做无差别强制重写。
4. 只有被标记为“可热同步”的字段允许覆盖到已有实例。
5. 结构性字段变更一律不热同步。

“可热同步”的典型字段包括：

- 描述文本
- 展示名
- 非关键对话文本
- 商店售价
- 掉落权重
- 非战斗中的基础刷新参数

“不可热同步”的典型字段包括：

- 主键与引用关系
- 房间出口拓扑
- 实例拥有者
- 已结算的角色状态
- 战斗中的技能队列
- 交易中的锁定物品

对于已加载实例，允许的同步时机如下：

- 下次刷新时
- 脱离战斗后
- 脱离对话后
- 场景重新加载时
- 运营后台显式执行安全刷新时

以下实例默认进入“保护态”，不接受自动覆盖：

- 玩家角色
- 活跃战斗中的 NPC
- 活跃交易中的物品
- 正在执行中的任务上下文对象

每次热更新至少输出以下结果：

- 变更的定义清单
- 受影响实例数量
- 已同步实例数量
- 未同步实例清单
- 未同步原因

## 七、LPC MUDLib 转换器

### 7.1 转换目标

首个目标为 XKX100。

XKX100 是首个转换目标，但不属于首发闭环前置条件。

转换策略为一次性导入，不保持与源 MUDLib 的持续同步。

### 7.2 已知参考样本

以下 MUDLib 作为兼容性参考样本。

它们的存在意义不是承诺全部支持。

它们的意义是帮助定义更广覆盖的内容框架与转换器弹性。

| MUDLib | 主题 | 规模判断 | 当前定位 |
|:---|:---|:---|:---|
| XKX100 侠客行 | 武侠 | 中大型 | 首个目标 |
| ES2 东方故事2 | 武侠 | 小型 | 参考样本 |
| 风云2005 | 武侠 | 大型 | 参考样本 |
| 小雨西游 | 西游 | 大型 | 参考样本 |
| 神话世界·西游记 | 西游 | 大型 | 参考样本 |
| 炎黄群侠传 | 武侠 | 大型 | 参考样本 |

### 7.3 样本驱动下的转换结论

本地样本已经说明以下事实：

- 转换器不能把固定目录结构当作前提。
- 转换器不能把“技能只在一个目录中”当作前提。
- 转换器不能假设房间只存在于 `d/区域`。
- 转换器不能忽略 `include`、宏、路径别名与继承层。
- 转换器不能把巫师目录、建造模板、私有区域与正式世界内容混为一谈。

因此，转换器必须先做“发现与分类”，再做“抽取与归一化”。

### 7.4 转换总原则

- 先转结构与静态数据。
- 再转规则与脚本骨架。
- 复杂逻辑允许生成“人工适配清单”。
- 不追求对 LPC 运行时的完整模拟。
- 不为了单一 MUDLib 牺牲通用内容模型。

### 7.5 转换前发现阶段

在正式抽取内容前，转换器必须先完成发现阶段。

发现阶段至少包括：

1. 根目录与 world-root 识别。
2. 编码与文件扩展名识别。
3. include 搜索路径识别。
4. 宏文件与全局路径宏识别。
5. 继承基类与标准基类识别。
6. 语义目录分类。
7. daemon / class / skill / condition 命名空间识别。
8. 可疑动态生成目录与私有目录识别。

### 7.6 转换管线

转换流程如下：

1. 源码扫描
2. 根目录与语义目录发现
3. include / 宏 / 路径别名抽取
4. 继承关系分析
5. Daemon / Class / Skill / Condition 引用识别
6. 房间 / NPC / 物品 / 技能 / 条件转中间表示
7. 中间表示生成目标数据与适配骨架
8. 生成人工适配报告
9. 导入并校验

### 7.7 中间表示设计要求

转换器必须先生成稳定的中间表示，而不是直接把源代码翻成目标运行时对象。

中间表示至少应覆盖以下定义：

- `SourceFile`
- `MacroRef`
- `IncludeRef`
- `InheritRef`
- `AreaDef`
- `RoomDef`
- `ExitDef`
- `NPCDef`
- `ItemDef`
- `SkillDef`
- `SkillActionDef`
- `PerformRef`
- `ConditionDef`
- `QuestRef`
- `ShopDef`
- `DialogueRef`
- `DaemonRef`
- `CommandRef`
- `UnresolvedBehavior`

其中：

- `RoomDef` 至少应保留 `short`、`long`、`exits`、`objects`、`item_desc`、区域归属、可选坐标、可选地图标签。
- `NPCDef` 至少应保留基础属性、技能映射、门派 / class、装备装载、聊天脚本引用。
- `ItemDef` 至少应保留分类、装备位、可用效果、价值、绑定与来源。
- `SkillDef` 至少应保留技能类型、可用部位、基础 action、学习 / 练习条件、perform / exert 引用。
- `UnresolvedBehavior` 必须保留来源文件、位置、原因、影响级别与建议处理方式。

### 7.8 自动转换范围

可自动转换的内容包括：

- 房间与出口拓扑
- 静态 NPC / 物品属性
- 区域结构
- 技能基础定义
- 技能 action 列表与基础表现文本
- `valid_enable`、基础学习条件、基础练习消耗等可抽取规则
- `SKILL_D`、`CLASS_D` 等路径宏引用
- `item_desc`、`objects`、可选 `coor/x` `coor/y` `coor/z` `map` 等场景字段
- 商店货品清单
- 纯配置型对话与文本
- 门派 / class / 师承的基础归属关系
- condition 的基础定义与挂载关系

### 7.9 半自动转换范围

需要人工审核的内容包括：

- 战斗公式
- 特殊技能效果
- Daemon 行为
- 复杂任务条件
- 跨文件动态调用
- 数据库存取代码
- `call_out`、`heart_beat`、临时变量驱动的状态机
- 动态房间、迷宫模板、玩家建造区、私有房屋
- 巫师工作区 `u/` 中应否纳入正式内容
- 与命令系统深度耦合的玩法入口
- 使用 `perform_action`、`exert_function`、自定义 combat helper 的复杂技能链

### 7.10 高风险但应被识别的内容

以下内容即使不能首轮自动转换，也必须在扫描结果中被识别和归类：

- `F_MASTER`、`F_VENDOR`、`F_DEALER` 等 NPC 角色能力
- `replace_program(ROOM)` 这类优化写法
- build 模板、私有房、动态迷宫
- 命令分层与权限级别
- 通过 include 宏隐藏的路径引用
- 以 daemon 持有运行时状态的系统
- 技能子目录中的 perform 文件

### 7.11 不纳入 V1 的能力

- 不做 LPC 代码即时解释执行。
- 不做源 MUDLib 双向同步。
- 不保证 100% 保留原行为细节。

### 7.12 转换配置项

转换器需支持以下配置：

- mudlib 根目录偏移
- world 根目录偏移
- 文本编码策略
- 语义目录映射
- 基类路径映射
- 技能目录映射
- Daemon 路径映射
- Class 路径映射
- Condition 路径映射
- include 搜索路径
- 宏入口文件
- API 风格识别
- 动态内容目录排除规则
- 私有目录导入策略
- 特殊文件排除规则
- 保存文件导入策略

### 7.13 输出产物

每次转换至少输出：

- 扫描统计报告
- 语义目录识别报告
- 结构化内容数据
- 中间表示数据
- 规则骨架代码
- 转换日志
- 未适配项清单
- 风险分级报告
- 导入校验报告

### 7.14 XKX100 最小验收标准

XKX100 的最小验收标准定义如下。

达到以下条件，即视为“首轮转换闭环成立”：

1. 能完成源码扫描并输出基础统计报告。
2. 能识别 mudlib 根目录、include 搜索路径、技能 / daemon / class / condition 命名空间。
3. 能输出继承关系、宏引用、Daemon 引用报告。
4. 能把房间、出口、静态 NPC、静态物品、基础技能定义转换为结构化中间表示。
5. 中间表示中能保留房间描述、出口、对象刷点、可选坐标 / 地图标签、NPC 技能映射、基础 perform 引用。
6. 能导入一个可指定样板区域到目标数据库。
7. 进入游戏后，玩家可在该样板区域执行查看与移动。
8. 样板区域中的 NPC 与物品可被正确加载与展示。
9. 所有未支持逻辑必须进入未适配清单。
10. 不允许静默跳过关键对象而不留痕迹。

以下内容不属于首轮最小验收范围：

- 原战斗公式完全等价
- 原任务链完全可玩
- 原 Daemon 行为完全复现
- 原数值平衡完全一致
- 全量世界一次性无人工接入导入
- 巫师工作区与私有建造区的完整复原
- 所有玩家命令的逐条兼容

## 十、游戏内容设计

### 10.1 角色系统

#### 10.1.1 角色属性分层

角色属性建议采用多层结构，而不是单一数值平铺。

| 属性层 | 典型字段 | 设计意图 |
|:---|:---|:---|
| 先天资质 | 根骨、悟性、福缘、容貌等 | 影响成长倾向与内容判定 |
| 后天属性 | 力量、敏捷、体质、精神等 | 直接参与战斗与交互 |
| 动态状态 | 气血、内力、精力、体力等 | 在战斗和行动中实时变化 |
| 身份关系 | 门派、阵营、声望、称号等 | 影响可学内容、NPC态度与剧情 |

#### 10.1.2 成长层次

内容层允许采用“经验 - 等级 - 境界”复合成长。

但引擎不应把某一种成长公式硬编码成唯一方案。

| 层次 | 示例 | 作用 |
|:---|:---|:---|
| 经验 | 战斗、任务、修炼获得 | 推动基础成长 |
| 等级 | 1-100 或其他区间 | 解锁基础内容门槛 |
| 境界 | 入门、精进、宗师等 | 承载武学层次与剧情门槛 |
| 声望 / 组织身份 | 门派职位、江湖名望等 | 承载社会性进度 |

### 10.2 内力与经脉系统

内力系统是武侠题材的重要差异化内容。

框架层建议支持以下对象：

- 丹田容量
- 当前内力
- 内力恢复
- 经脉通达度
- 内功冲突关系
- 走火入魔风险

| 子系统 | 核心机制 | 设计意义 |
|:---|:---|:---|
| 丹田容量 | 决定内力上限 | 资源管理核心 |
| 经脉系统 | 影响运转效率与解锁条件 | 形成成长路径差异 |
| 内力属性 | 阴阳刚柔等属性标签 | 影响技能联动与克制 |
| 风险系统 | 透支、冲突、干扰时触发异常 | 提供收益与风险权衡 |

### 10.3 武学系统

#### 10.3.1 武学数据模型

| 层级 | 数据实体 | 核心字段 |
|:---|:---|:---|
| 武功 | 招式集合 | 名称、来源、类型、品质、学习条件 |
| 招式 | 具体技能 | 消耗、冷却、伤害公式、效果标签、前置条件 |
| 内功 | 心法修为 | 层数、运转效果、冲突关系、恢复效率 |
| 轻功 | 位移与身法 | 速度修正、闪避修正、地形通行能力 |
| 天赋 | 被动成长 | 节点、解锁条件、效果组合 |

#### 10.3.2 武学成长链条

内容层可以支持以下成长阶段：

| 阶段 | 达成条件 | 核心收益 |
|:---|:---|:---|
| 学习 | 获得秘籍或拜师 | 解锁基础形态 |
| 熟练 | 反复使用或修炼 | 提高系数，降低消耗 |
| 精通 | 熟练度满或通过考验 | 解锁强化方向 |
| 变招 | 特定条件下领悟 | 获得情境技能效果 |
| 自创 | 多体系融合后开放 | 形成独门技能路线 |
| 传承 | 通关或重大节点 | 进入长线内容循环 |

### 10.4 即时制战斗系统

#### 10.4.1 核心结论

V3 明确只做即时制战斗。

不做回合制。

不做限时回合制。

不做多战斗模式切换。

#### 10.4.2 即时制基本规则

即时制战斗采用“事件驱动 + 独立冷却 + 轻量 Tick”的实现方式。

每个技能拥有独立 cooldown。

只要技能未在冷却中，就可以尝试释放。

除非某个技能、BUFF 或控制效果另行施加限制，否则不设置全局公共冷却作为默认规则。

#### 10.4.3 技能释放校验

技能可释放不只取决于冷却。

还必须校验：

- 资源是否足够
- 目标是否合法
- 距离是否满足
- 当前状态是否允许
- 是否被控制或打断
- 武器 / 姿态 / 内功前置是否满足

#### 10.4.4 战斗可支持的效果类型

| 效果类型 | 示例 |
|:---|:---|
| 直接伤害 | 单体、群体、持续伤害 |
| 治疗恢复 | 气血恢复、内力恢复 |
| 控制效果 | 定身、击退、沉默、眩晕 |
| 强化效果 | 攻击提升、防御提升、速度提升 |
| 弱化效果 | 易伤、减速、封脉、内力紊乱 |
| 位移效果 | 突进、后撤、闪现、拉拽 |

#### 10.4.5 招式克制与标签体系

内容层允许存在招式类型克制。

但引擎应优先提供通用标签体系，而不是把固定六角克制写死在内核里。

例如可支持：

- 拳、掌、指
- 剑、刀、棍
- 火、冰、毒、暗器
- 刚、柔、阴、阳

#### 10.4.6 环境互动

战斗系统应允许环境因子参与规则计算。

| 环境因子 | 可能影响 |
|:---|:---|
| 地形 | 高处命中、狭窄区域位移受限、水域技能限制 |
| 天气 | 雨雪风雾对命中、火系、暗器等产生修正 |
| 光照 | 夜间命中、潜行、视野范围变化 |
| 房间标签 | 擂台、安全区、禁武区、轻功区等特殊规则 |

### 10.5 物品与装备系统

| 物品类型 | 典型槽位 / 用途 | 设计重点 |
|:---|:---|:---|
| 武器 | 主手 / 副手 | 招式加成、耐久、类型限制 |
| 防具 | 头 / 身 / 腰 / 腿 / 足 | 减伤、抗性、套装效果 |
| 饰品 | 项链 / 戒指 / 玉佩等 | 属性加成、被动效果 |
| 药品 | 快捷使用 | 冷却、共享限制、耐药性 |
| 材料 | 背包堆叠 | 锻造、炼丹、任务消耗 |
| 秘籍 | 学习与领悟 | 绑定、消耗、阅读条件 |
| 任务物品 | 特殊栏位或背包 | 不可丢弃或受限丢弃 |

建议支持以下附加机制：

- 耐久度
- 绑定规则
- 堆叠规则
- 品质与稀有度
- 使用条件
- 来源追踪

### 10.6 地图与移动系统

#### 10.6.1 房间图原则

V1 以房间图为核心。

地图节点是 Room。

连接边是 Exit。

数据层允许房间带 `z` 坐标。

#### 10.6.2 坐标与空间层次

| Z 值示意 | 场景 | 用途 |
|:---|:---|:---|
| Z > 0 | 屋顶、树冠、高空 | 轻功、伏击、特殊移动 |
| Z = 0 | 地面 | 常规移动主层 |
| Z < 0 | 地下、密室、洞穴 | 隐藏区域与特殊探索 |

#### 10.6.3 寻路

自动寻路仅支持房间图级别的 A*。

路径权重可考虑：

- 距离
- 危险度
- 通行条件
- 区域权限

MVP 不实现复杂区域流式加载系统。

### 10.7 声望、门派、帮派与组织系统

框架层应区分至少三类关系：

- 阵营关系
- 门派关系
- 帮派 / 组织关系

| 维度 | 典型范围 | 影响 |
|:---|:---|:---|
| 正邪值 | 连续数值或离散阵营 | NPC态度、剧情分支 |
| 门派贡献 | 各门派独立 | 武学兑换、职位晋升 |
| 个人好感 | 面向特定 NPC | 任务、对话、支援 |
| 江湖传闻 | 行为传播结果 | 初始态度、遭遇事件 |
| 帮派关系 | 玩家组织维度 | 频道、活动、身份协作 |

首发闭环只要求：

- 基础声望
- 基础门派或阵营归属

帮派系统不作为首发前置。

### 10.8 世界动态

#### 10.8.1 时间系统

| 时间维度 | 作用 |
|:---|:---|
| 昼夜循环 | 影响描述、视野、NPC 位置 |
| 季节变化 | 影响文本、资源、部分规则 |
| NPC 作息 | 影响出现地点与可交互窗口 |

MVP 至少支持昼夜切换与基础 NPC 作息。

#### 10.8.2 随机遭遇

| 遭遇类型 | 触发机制 | 内容示例 |
|:---|:---|:---|
| 路见不平 | 移动中概率触发 | 介入或旁观 |
| 奇遇事件 | 地点 + 条件触发 | 秘籍、隐士、密道 |
| 秘境入口 | 时间或任务触发 | 限时探索 |
| 追杀事件 | 声望或任务后触发 | 高危战斗与奖励 |

#### 10.8.3 因果与长期分支

因果系统、复杂多结局与大规模世界演化属于长期目标。

V1 只要求保留可扩展位置，不要求完整实现。

### 10.9 聊天系统

首发至少支持：

- 公共频道
- 私聊

后续扩展支持：

- 门派频道
- 帮派频道
- 队伍频道
- 系统公告频道

### 10.10 经济系统

框架层建议支持以下经济对象：

- 多级货币
- NPC 商店
- 玩家交易
- 掉落产出
- 修理与消耗回收

首发闭环只要求：

- 基础货币
- NPC 商店或最小购买行为
- 基础掉落

玩家交易建议保留接口，但不强制首发完成。

### 10.11 音效与表现扩展

首发不以音效为主。

但框架应预留以下能力：

- 背景音乐开关
- 事件音效开关
- 音量分级配置
- 图片与图标插槽

## 十一、首发闭环与阶段范围

### 11.1 首发闭环目标

首发闭环的目标不是一次做完整武侠世界。

首发闭环的目标是打通“可登录、可进世界、可移动、可战斗、可聊天、可编辑内容”的最小可玩链路。

### 11.2 首发闭环必做能力

- 基础账号登录
- 角色创建
- 房间 / 出口 / 场景浏览
- 基础移动与查看
- 公共聊天与私聊
- 背包、装备、物品使用
- 基础即时制 PvE 战斗
- Web 管理后台基础内容编辑
- 一个最小可玩区域

### 11.3 首发闭环不包含的能力

以下能力明确移出首发闭环：

- 短信验证码
- 微信授权登录
- 帮派系统
- XKX100 首轮转换验收

以下能力建议也不作为首发闭环前置：

- 组队
- 玩家交易
- 复杂任务链
- 复杂门派体系
- 大型世界事件

### 11.4 首发区域建议

首发区域应满足以下标准：

- 有至少一段完整进入世界路径
- 有若干房间与出口
- 有至少一类敌对 NPC
- 有至少一类可拾取或可使用物品
- 有至少一条最小任务或引导流程
- 有后台可编辑与发布的内容样本

### 11.5 首发后迭代方向

- 组队
- 玩家交易
- 门派与帮派体系
- 手机号与微信登录
- XKX100 首轮转换闭环
- 更复杂的武学联动
- 自创武学
- 多周目与传承
- 音效与图形化增强

## 十二、后台管理需求

### 12.1 内容制作

- 房间、出口、区域编辑
- NPC 编辑
- 物品编辑
- 武学与招式编辑
- 任务编辑
- 世界事件配置
- 商店与掉落配置
- 对话树与触发条件配置

### 12.2 运营管理

- 账号查询、封禁、解封
- 角色数据查看与修正
- 在线状态查看
- 公告发布
- 敏感操作审计

### 12.3 数据与巡检工具

- 批量导入导出
- 转换器结果校验
- 数据一致性巡检
- 失效引用检测
- 内容发布差异对比
- 热更新同步结果查看

### 12.4 后台权限层次

后台建议至少区分以下角色：

- 超管
- 运营
- 内容编辑
- GM / 客服
- QA / 只读巡检

这些角色属于 `PlatformRole`，不属于玩家侧 `GameAccount` 权限。

## 十三、非功能性要求

### 13.1 安全性

- 全站 HTTPS / WSS
- 服务端权威计算
- 接口限流
- 权限分层
- 操作审计
- 常见输入过滤与校验
- 后台与玩家认证边界分离

### 13.2 稳定性

- 关键异常隔离
- 优雅停机
- 自动重启
- 定时备份
- 恢复演练
- 长连接异常回收
- 关键状态回写失败时有补救策略

### 13.3 可观测性

- 分级日志
- 结构化日志
- 核心指标监控
- 在线连接数监控
- 慢查询监控
- 任务失败告警
- 战斗错误与协议错误统计

### 13.4 测试要求

- 单元测试覆盖核心规则
- 集成测试覆盖登录、移动、战斗、聊天
- 转换器测试覆盖样例 MUDLib
- 后台关键操作有回归测试
- 上线前执行并发压测

### 13.5 性能与扩展性原则

- 只为单实例优化，不为分布式扩展提前设计过重机制。
- 优先优化房间广播、战斗结算、路径查询、内容加载四类热点。
- 允许后续增加缓存层，但不得让缓存先于数据库成为事实真源。

## 十四、部署方案

### 14.1 开发环境

- 本机开发
- PostgreSQL 本地实例
- 微信开发者工具联调

Redis 与 Celery 在开发环境中不是强制项。

### 14.2 测试环境

- 接近生产的 Linux 环境
- 与生产同版本 PostgreSQL
- 独立域名或测试子域名

若测试阶段需要验证 Redis channel layer 或限流，再引入 Redis。

### 14.3 生产环境

首发推荐部署形态如下：

- Nginx
- Daphne
- Django / Channels 应用
- PostgreSQL
- systemd 或 Supervisor

按需引入的可选组件如下：

- Redis
- Celery Worker
- Celery Beat

### 14.4 备份策略

- PostgreSQL 定时备份
- 关键配置文件备份
- 转换结果与导入报告归档
- 发布前后关键数据快照

### 14.5 运维原则

- 首发以单实例稳定运行为第一目标。
- 不为了“未来可能上多实例”而提前引入复杂协调层。
- 任何新增基础设施都必须有明确收益与维护边界。

## 十六、当前确认项

- 采用自研引擎路线
- 不使用 Evennia 运行时
- `evennia-main/` 仅作为本地参考源码
- 保留 Evennia 设计思想借鉴
- 前端采用 uni-app + Vue 3
- 首发支持 H5 与微信小程序
- 后端正式环境统一采用 PostgreSQL
- 只做单实例
- 不做多实例水平扩展
- 只做即时制战斗
- 每个技能独立 cooldown
- 首个转换目标为 XKX100
